# 二、设计模式解决的核心问题

绝大多数模式都在围绕三个问题工作：

```mermaid
flowchart TB
    Problem["复杂系统的三类核心问题"]

    Problem --> Change["变化"]
    Problem --> Dependency["依赖"]
    Problem --> Failure["失败"]

    Change --> C1["哪些部分稳定？"]
    Change --> C2["哪些部分经常变化？"]
    Change --> C3["如何把变化限制在局部？"]

    Dependency --> D1["谁依赖谁？"]
    Dependency --> D2["依赖具体实现还是抽象契约？"]
    Dependency --> D3["能否独立替换？"]

    Failure --> F1["失败能否隔离？"]
    Failure --> F2["能否重试或回滚？"]
    Failure --> F3["是否存在备用方案？"]

    C3 --> Encapsulation["封装变化"]
    D3 --> Decoupling["降低耦合"]
    F3 --> Resilience["建立恢复能力"]

    Encapsulation --> Goal["可理解、可扩展、可维护的系统"]
    Decoupling --> Goal
    Resilience --> Goal
```

其统一公式可以表示为：

```mermaid
flowchart LR
    Stable["稳定部分"] --> Contract["抽象接口 / 契约"]
    VariableA["变化实现 A"] --> Contract
    VariableB["变化实现 B"] --> Contract
    VariableC["变化实现 C"] --> Contract

    Contract --> System["系统主体"]

    Change["需求发生变化"] --> Replace["增加或替换实现"]
    Replace --> VariableC
    Replace -. "尽量不修改" .-> System
```

生活中的对应结构：

```mermaid
flowchart LR
    Goal["稳定目标：保持健康"] --> Mechanism["抽象机制：可持续运动"]
    Mechanism --> Running["跑步"]
    Mechanism --> Swimming["游泳"]
    Mechanism --> Cycling["骑车"]
    Mechanism --> Strength["力量训练"]

    Injury["膝盖受伤"] --> Switch["切换具体策略"]
    Switch --> Swimming
    Switch -. "目标不变" .-> Goal
```

这里的核心是：

> 不要把“目标”与“某一种实现方式”永久绑定。

```mermaid
flowchart TB

    SOLID --> ISP["I：接口隔离"]
    SOLID --> DIP["D：依赖倒置"]

    SRP --> SRP1["不同变化原因分开"]
    SRP --> SRP2["一个模块围绕一个主要职责"]

    LSP --> LSP2["不能破坏原有行为契约"]

    ISP --> ISP1["接口小而明确"]
    ISP --> ISP2["不强迫依赖无关能力"]

    DIP --> DIP1["高层策略依赖抽象"]
    DIP --> DIP2["低层细节实现抽象"]
```

## 1. 单一职责原则

错误结构：

```mermaid
flowchart TB
    Order["订单对象"]

    Order --> Price["计算价格"]
    Order --> Database["保存数据库"]
    Order --> Email["发送邮件"]
    Order --> Invoice["生成发票"]

    PriceChange["价格规则变化"] --> Order
    DBChange["数据库变化"] --> Order
    EmailChange["通知渠道变化"] --> Order
    InvoiceChange["发票格式变化"] --> Order
```

一个模块同时被四种原因修改，容易越来越臃肿。

拆分后：

```mermaid
flowchart LR
    Order["Order<br/>订单数据与业务规则"]

    Order --> Pricing["PricingService<br/>价格计算"]
    Order --> Repository["OrderRepository<br/>数据保存"]
    Order --> Notifier["Notifier<br/>消息通知"]
    Order --> Invoice["InvoiceGenerator<br/>发票生成"]

    PriceChange["价格变化"] --> Pricing
    DBChange["数据库变化"] --> Repository
    NoticeChange["通知变化"] --> Notifier
    FormatChange["格式变化"] --> Invoice
```

生活中的单一职责：

```mermaid
flowchart TB
    Personal["个人管理系统"]

    Personal --> Calendar["日历<br/>时间约束"]
    Personal --> Todo["待办系统<br/>具体行动"]
    Personal --> Notes["笔记系统<br/>知识信息"]
    Personal --> Review["复盘系统<br/>分析反馈"]
    Personal --> Finance["财务系统<br/>资金资源"]
```

## 2. 开闭原则

不符合开闭原则：

```mermaid
flowchart LR
    NewPayment["增加一种支付方式"] --> Modify["修改订单核心代码"]
    Modify --> TestAll["重新测试整个订单系统"]
    TestAll --> Risk["引入回归风险"]
```

符合开闭原则：

```mermaid
classDiagram
    class OrderService {
        +checkout(payment)
    }

    class Payment {
        <<interface>>
        +pay(amount)
    }

    class WeChatPayment {
        +pay(amount)
    }

    class CardPayment {
        +pay(amount)
    }

    class BalancePayment {
        +pay(amount)
    }

    class CryptoPayment {
        +pay(amount)
    }

    OrderService --> Payment
    Payment <|.. WeChatPayment
    Payment <|.. CardPayment
    Payment <|.. BalancePayment
    Payment <|.. CryptoPayment
```

增加新支付方式时，只增加新实现，不必修改订单核心流程。

## 3. 依赖倒置原则

错误依赖：

```mermaid
flowchart LR
    High["订单业务<br/>高层策略"] --> Low["微信支付 SDK<br/>低层细节"]

    Low --> BusinessChange["订单业务被迫修改"]
```

```mermaid

    WeChat["微信支付适配器"] --> Abstract

    Balance["余额支付适配器"] --> Abstract

    SDK1["微信 SDK"] --> WeChat
    SDK2["银行 SDK"] --> Card
    Storage["账户系统"] --> Balance
```

# 五、创建型模式图谱

创建型模式解决的是：

> 谁负责创建对象、创建哪种对象、以什么步骤创建。

```mermaid
flowchart TB
    Question["对象如何创建？"]

    Question --> Q1{"只需要集中创建逻辑？"}
    Q1 -- "是" --> SimpleFactory["简单工厂"]

    Question --> Q2{"由不同实现决定创建哪种产品？"}
    Q2 -- "是" --> FactoryMethod["工厂方法"]

    Question --> Q3{"需要创建一整族匹配产品？"}
    Q3 -- "是" --> AbstractFactory["抽象工厂"]

    Question --> Q4{"对象复杂且需要分步骤构建？"}
    Q4 -- "是" --> Builder["建造者"]

    Question --> Q5{"已有相似对象可供复制？"}
    Q5 -- "是" --> Prototype["原型"]

    Question --> Q6{"业务上要求作用域内唯一？"}
    Q6 -- "是" --> Singleton["单例"]
```

# 六、结构型模式图谱

结构型模式解决的是：

> 已有对象或模块如何组合，才能更容易使用和变化。

```mermaid
flowchart TB
    Q["当前遇到什么结构问题？"]

    Q --> A{"接口不兼容？"}
    A -- "是" --> Adapter["适配器"]

    Q --> B{"存在两个独立变化维度？"}
    B -- "是" --> Bridge["桥接"]

    Q --> C{"需要表达整体与部分？"}
    C -- "是" --> Composite["组合"]

    Q --> D{"需要动态增加功能？"}
    D -- "是" --> Decorator["装饰器"]

    Q --> E{"复杂子系统难以使用？"}
    E -- "是" --> Facade["外观"]

    Q --> F{"大量对象有公共状态？"}
    F -- "是" --> Flyweight["享元"]

    Q --> G{"需要控制真实对象的访问？"}
    G -- "是" --> Proxy["代理"]
```

## 2. 桥接模式

不使用桥接时容易发生组合爆炸：

```mermaid
flowchart TB
    Root["消息类型 × 发送渠道"]

    Root --> NormalEmail["普通邮件"]
    Root --> NormalSMS["普通短信"]
    Root --> NormalPush["普通推送"]
    Root --> UrgentEmail["紧急邮件"]
    Root --> UrgentSMS["紧急短信"]
    Root --> UrgentPush["紧急推送"]
```

桥接后：

```mermaid
classDiagram
    class Message {
        <<abstract>>
        -sender
        +send(content)
    }

    class NormalMessage
    class UrgentMessage

    class Sender {
        <<interface>>
        +send(content)
    }

    class EmailSender
    class SmsSender
    class PushSender

    Message <|-- NormalMessage
    Message <|-- UrgentMessage

    Message o--> Sender

    Sender <|.. EmailSender
    Sender <|.. SmsSender
    Sender <|.. PushSender
```

形成两个可以独立扩展的维度：

```mermaid
flowchart LR
    MessageType["消息类型<br/>普通 / 紧急 / 营销"] --> Combine["自由组合"]
    Channel["发送渠道<br/>邮件 / 短信 / 推送"] --> Combine
```

# 七、行为型模式图谱

行为型模式解决的是：

> 对象之间如何分工、通信、切换行为和传递请求。

```mermaid
flowchart TB
    Q["当前遇到什么协作问题？"]

    Q --> Q1{"请求要沿多个处理者传递？"}
    Q1 -- "是" --> Chain["责任链"]

    Q --> Q2{"请求需要记录、排队、撤销？"}
    Q2 -- "是" --> Command["命令"]

    Q --> Q3{"需要执行简单规则语言？"}
    Q3 -- "是" --> Interpreter["解释器"]

    Q --> Q4{"需要统一遍历集合？"}
    Q4 -- "是" --> Iterator["迭代器"]

    Q --> Q5{"多个参与者关系过于复杂？"}
    Q5 -- "是" --> Mediator["中介者"]

    Q --> Q6{"需要保存并恢复状态？"}
    Q6 -- "是" --> Memento["备忘录"]

    Q --> Q7{"一个变化要通知多个对象？"}
    Q7 -- "是" --> Observer["观察者"]

    Q --> Q8{"内部状态决定行为？"}
```

```text

限制耦合，隔离失败；
保存快照，准备补偿；
从简单开始，按反馈重构。
```
